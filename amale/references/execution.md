# Route and execute

Inspect `next`, then gather a short factual state. A task can need source inspection, web research, a scratch experiment, a compact plan or direct implementation. Ask Jev to select among eligible actions and configurations. Independent research targets can be separate tasks; research-only or plan-only requests end with evidence, not compulsory code.

Use `catalog` to obtain current model cards. Default candidates are latest stable GLM Flash and DeepSeek Flash. A purpose combines model, actual available tools, focused brief and appropriate checks. Filter for image input, tool support, context and access before asking Jev. Current price/capability is a sourced fact; quality and latency are uncertain until observed. Kimi K3 is for supported deeper needs, not all frontend/research. Do not force a cheap failure for a known hard task. Keep host work for tiny coupled tasks or escalated diagnosis.

Prepare isolated task workspaces using the host's supported worktree mechanism or Git worktrees. Preserve relevant uncommitted input explicitly; ordinary worktrees do not copy it. The runtime accepts the prepared absolute workspace; it does not guess a base branch or merge changes automatically. On non-Git projects, use host-controlled isolation/copy and explicit integration or serialize work. Never give independent workers the main writable checkout concurrently.

Claim before direct edits, or use `worker` for tracked pi execution. The worker brief must include applicable repository instructions, allowed scope, acceptance criteria, resources, references and real tools. Built-in pi tools do not include a general web-search connector: for web research, supply retrieved source artifacts or have the host use its retrieval tools and record results. For vision provide actual accessible image files and a verified image-capable model; do not infer appearance from source alone. Flash workers may use read on images when supported by pi.

Native subagents may be used when the host can supply the required model and clean context; record actual identities and outcomes through the same runtime. Respect capacity and resource locks. No nested delegation by default. Carry forward protocol metadata in pi sessions rather than rewriting message histories.

Run registered task checks. Review a coherent task, accept when current checks and review pass, then integrate actual changes through host tools. Inspect merge conflicts and cross-task interactions, record integration evidence, and run full relevant integration checks against the final result. Commit/PR/publication follow existing user authorization; Amale does not add authorization.

Do not stop at `next: review`, `repair`, `integrate`, or `verify-feature`: these are your next actions. Continue until `done` or an actual external blocker. While an asynchronous worker runs, advance independent work; reconcile live ownership before restarting anything.

## Automatic model routing

`worker` and `reviewer` automatically load current OpenRouter cards, filter eligible candidates and ask Jev to select the model before launch. Omit `model` to use this route; an explicit model is only an assertion and must match the recorded selection. Default worker candidates are the newest stable tool-capable Flash model in each of GLM and DeepSeek. Review candidates exclude the author's family. The runtime records eligible cards, price/capability data, decision and actual model in diagnostic/state evidence. It does not claim vendor descriptions prove quality or speed.

Pass `routing: {role, requiredInputs, contextTokens, evidence}` to select a configured purpose pool or impose additional requirements. A named role must exist in `pools`. Supply observed strengths, measured latency or other grounded suitability evidence in pool notes and routing evidence. A specialist pool may contain models outside the default families; the full live catalog is available. Deep repair enforces Kimi, and host-depth work returns native host takeover rather than launching another Flash worker.

A low-confidence or malformed Jev response returns `host-decision` without starting pi. Read the eligible options, record `host-decision`, then retry the same worker/reviewer input: the resolved decision is reused without another Jev call. `route` can preview and checkpoint selection before dispatch. Selecting `reassess` or finding no eligible candidates returns `route-blocked`; revise the task/pool/evidence, then route again. Service errors remain errors, not permission to bypass Jev.

Routing receipts bind task contract, repair cycle, dependencies, pool, requirements and (for review) the current content fingerprint. They are consumed once. Unrelated task checkpoints do not invalidate them. Changed inputs require a new route and supersede stale pending routing questions. Native host edits still use `claim` with the actual host identity; this automatic gate applies to pi worker/reviewer launches, not to a claim that pretends to launch a model.

Worker context is task-specific: it retains run intent/constraints, all unscoped settled decisions, the task's and dependency tasks' routing decisions, and dependency artifact references. It excludes unrelated task routing and the coordinator's global next-action instructions. Originals remain in the durable revision named by the packet. This does not truncate arbitrary decisions by age or replace pi's original session metadata.

Before loading catalog cards or asking Jev, worker routing checks dependency integration, worker capacity and live resource/workspace conflicts. `dispatch-blocked` names the prerequisite or owner to reconcile; it is not a model-suitability judgment. Retry after that condition clears. Claim still rechecks the same constraints transactionally because another task may start while routing is in progress.


## Network launch boundary

Before Jev, catalog, worker or reviewer calls, inspect the host's effective network permissions. On Codex, when networking is explicitly restricted, launch the required network operation using the host shell tool's supported `sandbox_permissions: "require_escalated"` request with a precise destination/payload justification. Do this before attempts in the blocked sandbox. Approval remains controlled by the host. On Claude or another host use its supported network-permission mechanism; never assume Codex flags exist there. No global config edits, permission bypass, proxy workaround or unsandboxed background helper.

Run `preflight workspace run-id input.json` once per current execution boundary. Input is `{network:"allowed",channel:"Codex approved shell invocation"}` only when that describes the actual launch. Use unknown when permission is uncertain. Restricted returns network-permission-needed without reading credentials or making requests. The actual probe sends only a fixed synthetic 1-versus-9 decision via the same adapter and pi credential source as ordinary Jev requests. It makes one attempt, bounded to ten seconds, and archives a credential-free result plus diagnostics. Ready means this probe succeeded; it neither grants persistent permissions nor proves pi worker availability. Keep subsequent network launches in the same approved boundary; ordinary commands do not inherit an earlier elevated call's permission. Subagents need the same instruction and must not silently revert to restricted launches.

If a permission request is denied, retain the blocker and explain the denial; do not relabel it as Jev uncertainty or try an indirect route. Separate network-unreachable (cause not proven), credentials-needed, credits-needed, provider-access-denied, provider-unavailable, jev-protocol-error and jev-verification-needed. Do not repeat a known permission denial as transient network retries. Existing normal request retries remain for actual transient failures.

Permission to run a synthetic probe is not permission to export repository content. Use the user's existing authorized scope for necessary task briefs/code/evidence and state it accurately in approval requests. An explicit export rejection must be resolved before sending that payload. Preflight is a host startup procedure; the runtime does not inspect or modify host permission policy and does not claim to enforce session identity.
