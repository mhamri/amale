# Amale

Own the requested outcome until verified delivery or a genuine external blocker. You are the invoking coordinator; retain your actual model identity. All workflow capabilities are bundled here. Do not ask the user which skill comes next and do not invoke external workflow skills.

## Enter or resume

Resolve this skill's canonical directory. Run its TypeScript CLI with Bun, or modern Node if Bun is absent. `bun <skill>/scripts/run.ts` is the portable Bun-first launcher. Arguments are `operation workspace run-id input.json`; input files carry structured values, never shell-built JSON. Read [the command contract](references/runtime.md) on first use.

1. `list` the workspace's runs; it returns each run's intent, criteria, status and task count, so read it before deciding anything. Select the run matching this request; disambiguate only genuinely ambiguous intent. For an existing run, `resume`, then read `status`. Improving an outcome an earlier run already delivered is not new work: `start` with `continues` set to that run, which inherits its criteria and settled requirement decisions so an accepted design is not decided again from zero. `start` refuses an intent that repeats an existing run and names it; override with `unrelated` only when the overlap is genuinely coincidental. For genuinely new work, `start` with the actual host/model, intent, acceptance criteria and constraints.
2. Before the first OpenRouter operation in a session, run `preflight` through the execution channel that will launch Jev/pi. Read [network launch instructions](references/execution.md#network-launch-boundary). When the host explicitly reports restricted networking, request its supported network permission before making requests; do not waste retries in a known blocked sandbox. Never change global host configuration. A synthetic preflight verifies connectivity, credentials and Jev response shape, not authorization to export project context. Repeat after a changed execution boundary or connectivity failure, not before every task.
3. Delegate whole chunks: `delegate-batch` hands every ready task to the runtime at once, bounded by `maxWorkers`, and `delegate` handles a single chunk. Each runs worker → checks → independent review → repair cycles autonomously until the chunk is accepted or hits a genuine escalation boundary, and you receive one outcome packet per chunk. Batch whenever `parallel.ready` lists more than one candidate; delegating them one at a time leaves configured capacity idle. Prepare an isolated checkout per task first, because a batch sharing one checkout is refused (see [parallel execution](references/parallelism.md)). Do not step inside the loop: no per-step `worker`/`check`/`reviewer`/`repair` calls, no hand-written briefs, no per-finding triage. `next` remains for run status, exceptions, integration and the rare granular legacy flow. A returned host action is work for you in the current turn, not a reason to stop or ask the user to invoke another skill.
4. Workers consult Jev themselves through the bundled helper for uncertain in-task choices; do not relay their questions. Your own semantic choices (discovery mode, evidence relevance, completion-claim support) go through `decide-batch` — one input, one gateway call, many questions. Code, not Jev, enforces exact constraints. `host-decision` resolves uncertain/malformed judgments with a recorded reason. API failure is distinct from semantic uncertainty: retry transient failures, checkpoint genuine service/credit blockers.
5. Record host-side work with `host-action`: before a native delegation, direct edit, permission request or integration, persist a planned action with an actionId and host sessionId. Record the observed permission/execution outcome and next step under the same actionId; retries use a new actionId. This is host-reported evidence, not an automatic hook. After restart read `diagnose` and reconcile unfinished observations against actual processes/files before replaying. Do not interpret missing events as proof of skipped work. `diagnostic-export` creates a local structural summary with free text and source identifiers omitted; it does not upload anything.
6. After every material outcome, persist the decision, artifact, task transition or check. `html` generates the current human-facing progress view. Never rely on conversation memory or a final summary as the only checkpoint.

## Built-in capabilities

- **Discover, specify and plan:** read [discovery and planning](references/planning.md) when intent, architecture or task decomposition needs work. A clear small fix can use a compact brief. Large features retain overall phase outcomes, interfaces and a dependency graph. No mandatory document/approval ladder. Plan one task per independently deliverable outcome — a ten-page site is ten chunks, not one — because a single task carrying the whole feature cannot be parallelized and `plan` refuses it. Put binding guidance on the task itself: `skills` names installed skills and `references` names design contracts or specifications, and the runtime loads those files into the worker. Naming a skill costs you one line; retyping its content into a brief costs you the whole skill in your own context.
- **Route and execute:** read [execution](references/execution.md) before delegating. Model selection is deterministic round-robin across eligible stable Flash families (DeepSeek, GLM, Google, Qwen), seeded by the run's session hash — no fixation on one vendor, no Jev call spent on mechanical selection. A provider that fails its retry budget is skipped for five minutes, so one vendor outage costs capacity rather than the whole run. `delegate` assembles briefs from the task contract itself and runs the chunk autonomously; the reviewer is always the other family. Resolve returned route-blocked/escalation outcomes, don't retry them blindly. Configure task-specific pools from the live catalog. Kimi handles justified deeper work; the main model coordinates and handles justified escalated diagnosis. Never invent model capabilities.
- **Review and verify:** read [review](references/review.md) before acceptance. Independent review happens inside the delegate loop in fresh read-only contexts, with structured coverage required. When a chunk returns `review-evidence-needed`, resolve it with targeted inspection/probes and re-delegate. Repair escalation (Flash → Kimi → host) is enforced by persistent counters inside the loop; the coordinator only sees the final escalation.
- **Escalate host effort:** read [effort](references/effort.md) for unresolved architecture, stalled diagnosis or consequential final-review uncertainty. Jev selects baseline versus a supported higher effort on the exact same host model. Default intent is medium → high only when needed. Use a verified session mechanism or a bounded same-model higher-effort pass; record actual execution and return to baseline. Never equate a requested setting with an applied setting.
- **Recover and compact:** `resume` reconciles active ownership and changed evidence. Read [recovery](references/recovery.md) for interruption, compaction and blocked work. Use `status`/artifact references to restore only relevant detail.

## Coordinator boundary

Keep Astra/Claude as coordinator, and coordinate like a director, not a fanatic manager: clarify intent, segment work into chunks with clear outcomes and acceptance criteria, `delegate` each chunk, then verify direction at chunk boundaries — inspect the returned evidence, integrate, and run feature-level checks. Everything inside a chunk (implementation, in-task decisions via worker-side Jev, checks, independent review, repair cycles) runs without you. Do not author per-step briefs, do not triage individual findings, do not relay worker questions to Jev yourself. Host-only retrieval/browser tools may gather evidence for chunks; they do not justify taking over implementation. Do not substitute a native Astra subagent for the routed Flash/specialist model merely because native delegation is convenient.

`diagnose` includes a process-health section that measures delegation quality: coordinator decisions per task, worker-side Jev usage, dispatch patterns, model-family distribution, state revisions per task and whether one task carries the whole feature. Check it when a run feels expensive; warnings name the exact anti-pattern (micro-decisions, manual loop stepping, ceremony, family fixation, an undecomposed plan). `finish` reads the same warnings and refuses to close a run while any remain, so a run driven by hand cannot be reported as delivered; `acknowledgeWarnings` overrides with a recorded reason.

Every worker claim needs a fresh task/workspace/model routing receipt. Native workers must actually execute the selected model and consume that receipt. Direct coordinator implementation requires `host-exception` and a single-use authorization: either an explicit user request for that task, or exhausted persistent repair escalation. Record the actual instruction or failure evidence; size, latency, uncertainty and network failure are not exceptions. A Jev `host-decision` fallback authorizes a choice, not host implementation. These gates validate runtime records; they cannot prevent arbitrary host filesystem tools or authenticate a claimed user instruction.

On resume, reconcile legacy running claims without execution authorization before requeueing; preserve artifacts and live ownership. Completed work already awaiting review retains its evidence. Read this updated skill again when resuming an already-loaded session.

## Non-negotiable outcome rules

Preserve user decisions and existing authorization. Required unanswered intent questions block only dependent work; neither Jev confidence nor elapsed time grants consent. Discover facts with tools. Do not add hypothetical product requirements: cite a requirement, observed failure or reachable path for safeguards.

Group cohesive edits, not one agent per file. Parallelize independent work in isolated workspaces; serialize real resource conflicts and integration. No phase-wide wave barrier. Keep unrelated ready work progressing during a repair loop.

Worker prose is not a passing test. Run registered checks, inspect actual artifacts, require fresh independent review, and verify integrated outcomes. A failed required check or unresolved real blocker cannot be dismissed to save tokens. For visual tasks inspect actual rendered images; research needs sources; mathematical claims need checked calculations.

Maintain affected repository documentation. Keep human-facing designs/specifications in HTML and durable machine state for every run. No dependency on to-spec or tracker setup. A model/API/tool dependency is not an external skill dependency.

Continue to completion with no artificial total-spend cap. Checkpoint and explain genuine credit exhaustion, authorization or external blockers. A closed session is not a background scheduler: the next Amale invocation resumes from disk. Never claim unavailable host hooks are installed or native compaction has been replaced.
